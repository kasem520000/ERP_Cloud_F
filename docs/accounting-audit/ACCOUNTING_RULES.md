# سجل القواعد المحاسبية

جميع البنود التالية ملاحظات مصدر لا نتائج محاسبية تشغيلية معتمدة.

| القاعدة | المصدر | الحالة وما يلزم |
|---|---|---|
| توازن المدين والدائن وحسابات قابلة للترحيل وفترة مفتوحة | accounting/accounting.service.ts: postJournalInTx وresolvePostingContext؛ schema/accounting.ts | يلزم اختبار عدم التوازن والإقفال والدقة والعكس |
| الأرصدة من اليومية لا من رسالة النجاح | journal_entries/journal_entry_lines؛ trialBalance/generalLedger/accountStatement | مراجعة معاملة الحالة posted والافتتاحيات والفلاتر مطلوبة |
| متوسط متحرك لكل صنف/مستودع | inventory.service.ts: recordInTx | قفل FOR UPDATE؛ كمية أساسية = كمية × عامل؛ الوارد يزيد القيمة بتكلفته، الصادر بالمتوسط، والعكس له تكلفة أصلية؛ لا نفترض FIFO |
| منع سالب المخزون له استثناء مصرح | recordInTx options.allowNegative؛ inventory.negative.override | اختبار سياسة المستأجر وصلاحية الاستثناء مطلوب؛ السالب ليس مرفوضاً مطلقاً |
| تكلفة الوصول توزع بالقيمة أو الكمية | purchases README وpurchases.service.ts | التقريب الموصوف HALF_UP أربع منازل، الباقي لأكبر أساس؛ يلزم مطابقة الكود والحركة والقيد |
| إنتاج اختياري الترحيل | inventory/production-posting.ts وتقرير الإنتاج | فحص ربط الطرفين قبل اعتماد GL للمخزون؛ عدم ربطهما قد يفسر فرقاً لا يجوز إخفاؤه |
| المستند والقيد مرتبطان بالمصدر | schema/accounting.ts؛ خدمات sales/purchases/treasury | اختبار عدم التكرار وذرية كل مسار ومردوداته مطلوب |
| الضرائب والعملة وسياسة التقريب | إعدادات المنشأة وملفات الترحيل؛ numeric(20,4) للحسابات | لا تفترض 15% ولا SAR ولا تطابق دقة التخزين مع العرض؛ لم تُقرأ إعدادات منشأة اختبار |
| التحويل النقدي مرحلتان وحساب نقد بالطريق | treasury README وtreasury.service.ts | إرسال ثم استلام، يلزم إثبات القيدين والأرصدة |
| الموافقات ليست مجرد زر | وحدات approvals وhandlers للمبيعات والمشتريات | يلزم أدوار مستقلة واختبار منع تجاوز الموافقة |

قرارات مطلوبة قبل اعتماد الدورة: سياسة المخزون الدائم/الدوري في تقارير الربح، الضرائب والاسترداد، العملة الأساسية ودقتها، تاريخ المستند مقابل تاريخ الترحيل، افتتاحيات الأطراف، معالجة مردودات تغير متوسطها ورسوم الشبكة. لا تختَر هذه السياسات لتصفير الفرق.


## تدقيق الدقة والربط — نقاط تتطلب متابعة
postJournalInTx يقبل فرقاً حتى 0.00005 قبل التخزين بأربع منازل ويشترط إجمالياً موجباً وعدد سطور >=2. لا يصح وصف ذلك «تساوياً مطلقاً»؛ يجب اختبار التقريب لكل سطر وقيد قاعدة البيانات بعد التخزين. فهرس journal_entries_source_idx عادي لا فريد، بينما journal_entries_idempotency_key فريد على المستأجر/المفتاح. غياب فهرس مصدر فريد ليس وحده عيباً: يجب اختبار أقفال وحالات كل خدمة والمفتاح الفعلي في طلبات الواجهات. فهرس فترات نشطة فريد جزئياً على المستأجر موجود، ولا يثبت وحده عدم تداخل فترتين غير نشطتين. مراجع SQL في DATABASE_CONSTRAINTS.md تحتاج مطابقة catalog قاعدة حية.

## تحقق الجولة الثانية — لا توازن دون صحة دلالية
- ثبت لهذه الحالة: المتوسط100؛ وارد12/1200 وصادر3/300؛ الرصيد9/900 يتطابق ledger/cache/GL، وحساب COGS300. المخزون الدائم هو المعالجة المنفذة في هذه الدورة (الأصل يزيد عند الشراء ويقل بالتكلفة عند البيع).
- VAT15% كتب صراحة في السطر وظهر180/67.50؛ البذرة تربط المدخلات والمخرجات بحساب2222001 واحد. لم تُختبر قانونية هذا الربط أو تصريح ضريبي خارجي.
- القيد المفرد توازن وارتبط بالمستند مرة واحدة، لكن كشف الأطراف جمع المقابلات أيضاً فصفّر الذمة؛ حقل partyId تحليلي لا يجوز جمع كل أرجل القيد منه كرصيد رقابي (ACC-002).
- إضافة900 مخزون ختامي إلى450−300 تخالف معالجة المخزون الدائم التي نفذها النظام نفسه (ACC-003). خيار عرض المخزون ليس إذناً بمضاعفة الربح.
- لقطة رأس فاتورة البيع cost_total=0 بينما سطرهاcost_total=300 وGL300؛ لا تعتمد رأس الفاتورة مصدراً للربح دون اتساق (ACC-004).
- التجريب الآجل لم يغير النقدية؛ فرق افتتاحيات البذرة بينGL/cache باقٍ (ACC-001). تقرير حركة الصندوق يقرأGL ويعرض50000/180000 صحيحين؛ API رصيد الموقع لا يقرأ نفس المصدر، ويجب حسم وظيفةcache قبل الإصلاح.
- اختبار رفض بيع99 أثبت تراجع إنشاء هذا المستند تحديداً: فاتورةبيع واحدة فقط بقيت، وحركتان للمخزون، وثلاثة قيود بما فيها الافتتاحي. لا يثبت كل مسارات الفشل الجزئي أو التزامن.
